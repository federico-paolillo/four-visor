# Autonomous Development Remediation

## Purpose

This document records changes to the durable inputs of the autonomous development
experiment so a future run can reach the current intended product without the
manual corrections that followed the original implementation goal.

Only these inputs are durable:

- `docs/SEED.md`, which defines the product and its locked constraints;
- the initial repository template, including `AGENTS.md`, `DECOMPOSE.md`, build
  tasks, container skeleton, documentation structure, and automation.

MADRs, User Stories, `docs/TODO.md`, traceability reports, and implementation
artifacts are generated byproducts. They must not become independent sources of
product truth. The remediation therefore changes how those artifacts are
generated rather than relying on corrections to a particular generated story.

US-019, the snapshot CLI, is excluded from this analysis because it was a
legitimate specification omission.

## Summary

The autonomous implementation generally followed its inputs correctly. Most
subsequent work came from five defects in those inputs:

1. Numeric requirements were specified independently without a workload or
   capacity model.
2. Observability described signals but not the operational questions those
   signals had to answer.
3. The template and decomposition process did not define firm boundaries for
   validation, documentation, release automation, or dependency ownership.
4. Later requirement changes bypassed the declared authority of the SEED,
   leaving the current generated artifacts inconsistent with the implementation.
5. Worker and Reviewer instructions rewarded exhaustive proof without requiring
   proportionality, a single enforcement owner, or a stopping rule. This led to
   tests for incidental log prose, repeated checks of the same invariant at
   several layers, bespoke smoke-like scripts, and comments that narrated
   obvious modules while non-obvious mechanisms remained unexplained.

The central remediation is to make the SEED quantitatively closed and to make
decomposition prove feasibility, cross-layer consistency, and operability before
it emits MADRs and stories.

## Intended Generated Outcome

A new decomposition and implementation run should produce the following current
behavior without later corrective stories:

- backend acquisition and synchronization default to four hours;
- the one-request-per-second global acquisition policy remains intact;
- Memcached has 2048 MiB available, 1 MiB items, disabled evictions, and enough
  capacity for active and incoming lineages to coexist;
- snapshot responses have no fixed absolute backend write deadline and are
  streamed by the repository edge;
- snapshot compression is applied exactly once by the VPS ingress, not by the
  backend or repository edge;
- the Collector keeps its sampling decision open for five hours;
- every synchronization trace and every error trace is retained, while
  approximately 10% of other successful traces are retained;
- acquisition, publication, and snapshot-serving failures are diagnosable from
  bounded, secret-free fields;
- attempted terminal upstream failures produce one warning each, undispatched
  deadline work is aggregate-only, and oversize resources are debug events;
- there is no application health/readiness endpoint or Compose health check;
- backend integration tests provision task-owned dependencies on ephemeral
  loopback-bound ports and do not require a prestarted project stack;
- the normal validation suite contains unit and integration tests, not smoke,
  end-to-end, or deployment tests;
- CI validates every push to `main`;
- manual CD publishes commit-identified Linux-amd64 images and a matching
  deployable archive with provenance, SBOMs, and attestations;
- README remains concise and operator-facing.

The generated plan should incorporate these requirements into the stories that
first introduce the affected behavior. It should not defer them to later
catch-all remediation stories.

## SEED Remediation

### 1. Establish one normative requirements section

The current SEED repeats defaults and locked behavior across requirements,
diagrams, operational flows, design notes, and summaries. A future SEED should
define every normative value once. Other sections may explain or illustrate the
rule but must refer back to its identifier instead of restating it.

Assign stable requirement identifiers, for example:

```text
ACQ-01  Global request-start interval
ACQ-02  Acquisition deadline
SCHED-01 Synchronization interval
CACHE-01 Required simultaneous lineage capacity
HTTP-01 Snapshot transfer deadline policy
OTEL-01 Trace-retention policy
```

Decomposition traceability must map these identifiers to generated acceptance
criteria. This is traceability within generated artifacts, not a new durable
source of truth.

### 2. Add a workload and capacity envelope

Add a normative section containing both formulas and initial values:

```markdown
## Production workload and budgets

- Outbound request starts are globally limited to one per second.
- One request attempt times out after five seconds.
- A request receives at most two transient retries with one- and two-second
  backoff; a longer valid Retry-After takes precedence.
- Acquisition and backend synchronization both default to four hours.
- A supported acquisition budget must complete the representative full workload
  without lineage-deadline failures and retain explicit headroom.
- Before changing acquisition defaults, record at least two consecutive native
  Linux-amd64 full acquisitions, including elapsed time, serialized bytes,
  resource counts, and controlled failure classes.
- Memcached must hold the active and incoming lineages simultaneously plus
  operational overhead. The deployment allocation is 2048 MiB, items are at
  most 1 MiB, lineage blocks are 512 KiB, and evictions are disabled.
- The representative production snapshot is the larger of the two most recent
  successful full acquisitions. Transfer, cache, and telemetry budgets are
  evaluated against that size.
```

The important requirement is the relationship between the values. The original
one-request-per-second policy and thirty-minute lineage deadline were mutually
incompatible for the observed workload. The initial 64 MiB Memcached allocation
likewise ignored the active-plus-incoming lineage model.

### 3. Add cross-layer duration and capacity invariants

Add explicit derived requirements:

```markdown
- The backend applies no fixed absolute write deadline to a successful snapshot
  response.
- The repository edge streams snapshot responses without imposing a shorter
  response timeout.
- The VPS ingress must allow preparation and transfer of the representative
  production snapshot.
- The backend and repository edge do not compress snapshot responses. The VPS
  ingress applies Brotli exactly once.
- The Collector tail-sampling decision window must exceed the configured
  acquisition deadline plus publication allowance. It defaults to five hours
  for the four-hour acquisition deadline.
- Cache TTL remains twice the synchronization interval, but TTL is cleanup
  insurance rather than a substitute for simultaneous-lineage capacity.
```

These are product invariants. Generated stories may decide implementation
mechanics only where the SEED leaves them open.

### 4. Replace signal-oriented observability with an operational contract

Retain the trace-first philosophy but add concrete diagnostic outcomes:

```markdown
## Operational diagnosis

For a synchronization-related failure, the Operator can determine:

- lineage correlation identifier;
- resource class;
- queue, rate, concurrency, request, body, decode, or retry stage;
- controlled error and cause types;
- bounded HTTP response status;
- retry attempt and exhaustion;
- publication stage or snapshot component where applicable;
- resulting operation and HTTP outcome.

Diagnostics never contain board or thread identifiers, raw URLs, response
bodies, cache keys or values, credentials, or raw dependency error strings.
```

Define event cardinality and severity:

```markdown
- Emit exactly one warning for every attempted resource fetch that terminates
  after its retry policy.
- Emit one aggregate terminal-failure record per lineage and bounded failure
  tuple.
- Work not dispatched before the lineage deadline is aggregate-only and is not
  reported as a fetch attempt.
- Oversize resources are expected contract states and emit debug events rather
  than warnings or errors.
- Local JSON stderr remains unfiltered. The OTLP branch exports only the
  specified lifecycle, warning, and error records with allowlisted attributes.
```

Define trace retention precisely:

```markdown
- Retain every complete synchronization trace.
- Retain every trace containing an error.
- Retain approximately 10% of other fully successful traces.
- Sampling occurs only in the OpenTelemetry Collector.
```

This lets decomposition allocate failure classification and lineage correlation
to acquisition, publication, and serving stories. The final telemetry story
should own SDK/Collector wiring and policy verification, not retroactively make
earlier boundaries diagnosable.

### 5. Correct the health model

Remove the health route, health command, DNS probe, Memcached probe, and Compose
health-check requirements from every SEED section. Replace them with:

```markdown
## Process and dependency status

4Visor exposes no application health or readiness endpoint and configures no
Compose health check. Upstream DNS and Memcached availability are operational
state, not process liveness. Process state, snapshot response status, logs,
metrics, and traces provide operational diagnosis.
```

The previous autonomous implementation was correct to build `/health` because
the original SEED required it. Avoiding that work requires changing the durable
requirement, not steering the implementation agents away from their story.

### 6. Define the delivery contract

Add the current release behavior to the SEED so decomposition does not explicitly
exclude it:

```markdown
## Continuous integration and release

- Every push to main runs all documented backend and frontend validation tasks.
- Releases are manually dispatched.
- One release builds Linux-amd64 backend and frontend images from the same exact
  commit and publishes immutable commit-derived tags.
- Published images include provenance and SBOMs and receive registry
  attestations.
- The release produces a deployable archive containing production Compose,
  Caddy, Collector configuration, an environment template tied to the same
  commit, and concise operator instructions.
- Operator instructions cover required configuration, start, upgrade, rollback,
  Memcached-loss recovery, and ingress timeout and Brotli ownership.
```

If a future project does not need CD, its SEED should exclude these items
explicitly. The template should not silently choose either outcome.

### 7. Define documentation ownership

Add:

```markdown
- README is limited to project purpose and actionable operator setup,
  configuration, operation, and troubleshooting.
- SEED owns product and architecture requirements.
- MADRs explain architectural choices that were genuinely open in the SEED.
- Generated stories own implementation acceptance criteria.
- Implementation invariants belong beside the code or in focused executable
  tests; they are not copied into README as story narratives.
```

This prevents every generated story from appending its internal design to
README and later requiring a documentation cleanup.

### 8. Define the validation boundary

Add:

```markdown
- Unit tests start no external process.
- Integration tests may start task-owned dependency containers using native
  container ports and Docker-assigned host ports bound to 127.0.0.1.
- Integration tests require no prestarted project stack and no fixed shared
  Compose project.
- Automated tests do not start the complete application deployment, exercise a
  browser end to end, or probe a deployed service.
- Native configuration rendering, image building, and release-archive assembly
  are build validation, not smoke or deployment tests.
- Bespoke structural validators are added only when the native tool cannot
  verify a required invariant.
```

This closes the ambiguity that produced large custom image, Compose, and
Collector validation systems which were later removed.

### 9. Require proportional verification and one policy owner

Add a testing and enforcement principle:

```markdown
- Test each behavior once at the lowest stable boundary that can prove it.
- Add a cross-boundary integration test only for behavior that can fail despite
  the lower-level test, such as serialization compatibility, dependency
  semantics, or framework wiring.
- Do not reproduce the same assertion in unit, integration, image, Compose,
  smoke-like script, and documentation checks merely as additional assurance.
- Negative-path coverage is required for trust boundaries, security rules,
  cancellation and concurrency, atomic data replacement, data-loss risks, and
  previously observed regressions. It is not required for every branch or log
  call.
- Log prose is not an API. Test exact text only when the text is itself a stable
  filtering or operator contract. Otherwise test severity, event identity,
  required fields, forbidden sensitive fields, and cardinality using one
  representative event per policy class.
- Each filtering, validation, and normalization policy has one authoritative
  enforcement layer. A second layer is allowed only for a distinct trust
  boundary or independently stated failure mode.
- Source-side telemetry filtering owns secrets, cardinality, and the application
  event catalogue. The Collector owns routing, batching, authentication, and
  trace sampling; it does not duplicate the application's field allowlists as a
  second failsafe.
- Test volume, branch count, mutation survival, and number of assertions are not
  goals. Stop when the acceptance criterion and material regression risks are
  proved.
```

For example, an OTLP policy needs one focused catalogue/filter test plus the
smallest representative producer check. It does not need every log-emitting call
to assert its complete string and attributes, followed by another Collector
filter suite and a full-stack capture script.

## Initial Template Remediation

### 1. Make the starter repository executable before decomposition

From a clean checkout, the template must pass every command it advertises. At
minimum verify:

- backend build, test, and lint;
- frontend build, test, lint, and type-check;
- supported first-party image builds;
- native Compose and Caddy configuration rendering;
- whitespace and generated-artifact cleanliness.

Provide one aggregate `mise run verify` task. CI should invoke that task rather
than duplicate a separate command list.

README, `AGENTS.md`, Mise, package scripts, and CI must use the same task names.
The initial template must not repeat the original `fe:typecheck`/`fe:check`
mismatch or reverse backend and frontend task lists.

### 2. Standardize artifact paths

Use these paths everywhere from the first commit:

```text
.agents/log/
.agents/planning/
docs/TODO.md
docs/madrs/
docs/stories/
```

Do not seed `.log/` or `.planning/` while the workflow writes under `.agents/`.
All coordinator, decomposition, and ignore-file instructions must agree.

### 3. Keep scaffolding minimal and verified

- Do not place guessed production capacity or timeout values in Compose or
  Collector configuration. Values must come from named SEED requirements.
- Prefer stock third-party images and native configuration over custom rebuilds.
- Include `.dockerignore` files and reproducible first-party Dockerfiles, but do
  not add custom image-validation frameworks.
- Keep all published example ports explicitly bound to `127.0.0.1`.
- Test-only containers use task-owned ephemeral loopback-bound ports.
- Never require `sudo`, privileged containers, firewall changes, or a shared
  prestarted dependency.

Worker and Reviewer guidance must also state:

- do not add a test solely to exercise every line, branch, log message, or
  defensive condition;
- reuse an existing test at the owning boundary instead of adding the same
  regression at every consumer;
- do not introduce a test seam, interface, fake, fixture family, or helper whose
  complexity exceeds the behavior it verifies;
- prefer deleting redundant checks when a stronger authoritative check already
  exists;
- validation ends when the story's observable acceptance criteria and material
  risks are covered.

### 4. Include CI; conditionally generate CD

The reusable template should contain minimal CI that runs `mise run verify` from
a clean checkout. CD should be generated or enabled only when the SEED contains
the release contract. Its configuration must use the same commit identity for
images, archive, environment, and release tag.

### 5. Add durable-input change control

Add this coordinator rule to `AGENTS.md`:

```markdown
When a requested correction changes a locked requirement, route, default,
delivery contract, or completed behavior, update the durable SEED first. Then
rerun or amend decomposition so the generated MADRs, stories, TODO assumptions,
and traceability agree before implementation begins. Do not implement a
specification reversal directly against stale generated artifacts.
```

Generated artifacts can be replaced. They must never silently override SEED.

### 6. Replace mandatory comments with a why-only policy

Remove the template rule requiring one comment for every module. It produces
comments such as “this module renders” or “this module owns” that restate names
without helping a maintainer.

Replace it with:

```markdown
Comment only information that cannot be recovered quickly from the code:
non-obvious invariants, security or compatibility constraints, protocol
ownership, calibrated limits, and why a simpler-looking implementation is
incorrect. Do not require file, module, function, or test comments merely for
coverage. Prefer a precise comment beside the constrained mechanism over a long
README explanation.
```

The Service Worker shell hash is the representative missed case. Its useful
comment should explain that paths and bytes are sorted and length-framed before
hashing so the cache name is deterministic, changes when any shell byte changes,
and cannot collide through ambiguous concatenation. A generic comment saying
that the file “injects its exact shell precache contract” does not preserve that
reasoning.

## Decomposition Prompt Remediation

`DECOMPOSE.md` should retain its multi-agent architecture, story, traceability,
and independent review roles, with the following required phases added.

### Phase 1: Template preflight

Before creating MADRs or stories:

1. Read the entire SEED and inventory normative requirement identifiers.
2. Compare the SEED with the actual template, canonical tasks, container
   configuration, documentation paths, and existing defaults.
3. Run the clean-checkout template validation entrypoint.
4. Record broken prerequisites and contradictions as blocking open questions.
5. Do not create stories that assume a broken prerequisite will somehow be
   corrected by a later story unless that correction is explicitly the first
   dependent story.

### Phase 2: Quantitative feasibility review

Before selecting defaults or closing open questions, calculate and record:

- request-count floor at the configured global rate;
- retry and timeout contribution to the acquisition budget;
- relationship between deadline and synchronization cadence;
- active-plus-incoming cache capacity and overhead;
- representative serialized snapshot size;
- backend, proxy, ingress, and client transfer constraints;
- trace duration versus Collector decision window.

An unknown that can be measured must not be resolved by invention merely to
produce zero open questions. Generate an early calibration/characterization
story or leave the question open. Calibration runs are one-off implementation
evidence, not a committed smoke or end-to-end test suite.

### Phase 3: Acceptance-level traceability

Section-level traceability is insufficient. For every normative requirement:

- identify the generated story that first implements it;
- identify the exact acceptance criterion that proves it;
- identify the canonical validation mechanism;
- identify downstream stories that consume the invariant;
- identify the durable documentation destination, if any.

Cross-cutting requirements such as observability, security, failure
classification, cancellation, and configuration must be implemented at the
boundary where the behavior originates. A final integration story may verify
the whole path but must not be the first owner of missing semantics.

### Phase 4: Cross-story invariant review

After ordering the proposed stories, a reviewer must trace these chains through
every consumer:

```text
request volume -> rate limit -> acquisition deadline -> schedule
snapshot size -> cache blocks -> simultaneous lineages -> Memcached capacity
snapshot size -> backend response -> edge proxy -> ingress transfer
sync duration -> root span lifetime -> tail-sampling decision window
failure boundary -> controlled classification -> log/metric/span -> operator query
commit identity -> image tag -> Compose environment -> release archive
```

No story set is approved while a downstream consumer imposes a smaller budget
than the operation it consumes.

### Phase 5: Semantic validation review

Review what each proposed validation actually does, not its label.

- Reject a full deployment probe called an "integration test."
- Reject large handwritten structural validators when a native parser or build
  command proves the requirement.
- Reject integration tests that depend on a shared Compose stack or fixed port.
- Reject documentation criteria without a named audience and destination.
- Reject acceptance criteria that cannot fail when the named behavior regresses.
- Reject duplicate tests of the same rule unless each test names a distinct
  failure mode unavailable at the other boundary.
- Reject exact log-line assertions unless the wording is an explicit operator or
  filtering contract.
- Reject duplicated application and Collector filtering unless they protect
  distinct trust boundaries.
- Reject reviewer findings whose only justification is untested code rather than
  an uncovered acceptance criterion or material regression risk.
- Require deletion or consolidation when a new authoritative check makes an old
  helper, fixture, script, or test redundant.

### Phase 6: Operability review

Before finalizing generated artifacts, the independent reviewer must answer:

1. Can the normal production workload finish within its budget?
2. Can active and incoming data coexist?
3. Can the representative snapshot traverse every HTTP hop?
4. Can each important production failure be diagnosed without secrets or
   unbounded cardinality?
5. Can a clean checkout run all canonical validation?
6. Are CI, release, and deployment consumption intentionally present or absent?
7. Do generated MADRs contain only genuine decisions left open by the SEED?
8. Does every generated story introduce a complete, currently operable slice?
9. Is each important rule enforced and tested at one clearly named owning
   boundary?
10. Does documentation explain the non-obvious reasons and omit narration that
    is already evident from names and control flow?

## Expected Story Allocation

Do not prescribe fixed story numbers, but steer decomposition toward these
ownership boundaries:

- acquisition stories own lineage correlation, controlled failure stages,
  terminal-warning cardinality, aggregated failures, and rate-capacity
  diagnosis;
- publication stories own controlled validation/write/pointer/cleanup failure
  classification and active serialized-size measurement;
- snapshot-serving stories own component/status diagnosis and unlimited
  successful response-write duration;
- scheduling stories own the four-hour acquisition/cadence relationship and
  startup effective-policy record;
- deployment stories own 2048 MiB Memcached capacity, streaming edge behavior,
  and single ingress-owned Brotli compression;
- observability integration owns the metric catalogue, OTLP filtering, five-hour
  Collector window, always-retained synchronizations, error retention, and 10%
  sampling of other successes;
- release automation is a first-class generated story when the SEED delivery
  contract is present;
- no generated story owns an application health endpoint.

This allocation should eliminate the need for a later US-020-style
diagnosability story and fold the corrective portions of US-021 into the stories
that introduce the affected behavior.

## Generated Artifact Acceptance Gate

Although generated artifacts are disposable, decomposition is not complete
until an independent reviewer confirms that they collectively satisfy the
durable inputs:

- every normative SEED requirement has acceptance-level traceability;
- no generated artifact contradicts a SEED default or exclusion;
- no MADR re-decides a locked SEED requirement;
- no story defers its required failure, observability, security, or cancellation
  behavior to a later cleanup story;
- no story invents a production constant without a requirement, formula, or
  calibration step;
- no story demands exhaustive branch, log-line, or implementation-detail tests;
- every repeated test or enforcement layer identifies a distinct failure or
  trust boundary;
- all dependencies point backward in the implementation order;
- the final generated plan includes template validation, production-budget
  validation, and release work when required;
- TODO contains no copied planning assumption that differs from the normative
  SEED requirement it references.

## Priority Order

1. Rewrite the SEED health, workload, capacity, transfer, observability, testing,
   documentation, and delivery sections.
2. Remove duplicated normative values from explanatory SEED sections.
3. Repair and validate the initial template task names, artifact paths, build
   skeleton, CI, and test-dependency model.
4. Add the preflight, feasibility, acceptance-traceability, cross-story, semantic
   validation, and operability phases to `DECOMPOSE.md`.
5. Run decomposition from scratch rather than manually preserving the current
   generated MADRs, stories, or TODO.
6. Review the newly generated plan against the Intended Generated Outcome above.
7. Only then begin a new autonomous implementation goal.

## Success Criteria

The remediation succeeds when a clean run from the revised SEED and template:

- generates no health-endpoint work;
- does not require later diagnosability or production-hardening stories;
- selects feasible linked time, memory, transfer, and telemetry budgets;
- produces self-contained tests without bespoke deployment-validation systems;
- verifies each rule proportionally at one authoritative boundary rather than
  accumulating duplicate failsafes;
- keeps README concise;
- documents non-obvious invariants instead of requiring ceremonial comments;
- includes the intended CI/CD path;
- and reaches the intended generated outcome without manual scope, logging,
  capacity, timeout, or delivery corrections.
